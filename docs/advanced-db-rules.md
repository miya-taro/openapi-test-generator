# DDL・期待値ルール・InfluxDB一括照合

「API連携・DB確認」で設定し、保存した試験定義をpytestで実行します。APIやDBから業務上の正解を推測する機能ではありません。正解となる参照・計算・変更範囲を人が指定します。

## PostgreSQL DDLを読み込む

1. 「DDLからテーブル・カラム一覧を読み込む」を開く。
2. 関連する複数テーブルの`CREATE TABLE`等を含む`.sql`ファイルを選ぶか、テキストを貼り付ける。
3. 「DDLを読み込む」を押すと、テーブル・型・NULL可否・既定値・生成列・主キー・外部キー・一意制約・CHECKが表示される。
4. 通常の対応付けや期待値ルールのテーブル名・単一カラム名入力で、候補を選べる。カラム候補は選択したテーブルのものだけを表示する。InfluxDBにはPostgreSQLのDDL候補を表示しない。複数カラムはカンマ区切りで入力する。

DDLは**解析だけ**行い、DB接続・テーブル作成・更新・削除は行いません。構造情報はブラウザーのローカル保存領域に保存します。「一覧を削除」で消せます。DDLからAPI項目への対応や計算式を自動設定しません。実DBの変更後はDDLも読み込み直してください。

対応はPostgreSQL形式、最大2MB。`CREATE TABLE`、`ALTER TABLE ADD COLUMN/ADD CONSTRAINT`、カラムの既定値・型・NULL可否変更に対応します。未対応の構造変更は警告し、不完全なテーブルを選択候補から外します。無修飾のテーブル名はpublicとして扱います。通常の対応付け候補はpublic内の英数字・アンダースコア名のみ。他schemaの構造は表示できますが、その参照には従来の期待値SQL等を使用してください。DDLに含まれていない参照先テーブルをDBから自動取得することはありません。

## 参照・計算・集計から期待値を作る

「確認する内容」で「参照・計算・集計から期待値を作って照合する」を選びます。

- APIに送るJSONと期待HTTP statusを入力する。空レスポンスも指定できる。
- 「処理を追加」で、期待値を作る処理を上から順に設定する。
- 「照合先を追加」で、レスポンス項目か実行後のDB取得結果と、期待値を指定する。
- 保存後、準備・レビュー・実行する。既存の認証設定も使用する。

### 入力値を10倍して保存する例

| 設定箇所 | 入力例 |
|---|---|
| 送信body | `{"id":1,"value":1.234}` |
| 処理名・種類 | `scaled`・計算 |
| 計算方法 | 掛け算 |
| 第1入力 | 項目を参照：`body.value` |
| 第2入力 | 固定値：`10` |
| 照合先 | 実行後のDB、対象テーブル、取得カラム`amount` |
| 検索条件 | `id = body.id` |
| 取得値のパス | `0.amount`（最初の1行のamount） |
| 期待値 | 項目を参照：`steps.scaled` |

取得値パスを空欄にすると全行を比較します。`0.amount`を選んだ場合は先頭行の値だけで、余分な行の不存在までは検証しません。全行・件数・重複を確認する場合は配列全体を照合してください。

### 別DBを順に参照する例

1. PostgreSQLの拠点表を`location_id`で検索し、`site_id`を得る。
2. 優先順ルールで、リクエストの`site_id`があればそれ、なければ検索結果を選ぶ。
3. 必要なら文字列化してInfluxDBのタグ値にする。
4. InfluxDBのmeasurementを拠点・期間・項目で検索する。
5. 項目ごとに合計し、レスポンスの配列と順序を無視して比較する。

SQLを手書きせず、参照先・条件・処理名・参照パスをフォームで設定できます。DBは各種類1接続先。参照結果を次の検索の値やIN条件に使用できます。

参照記法は`body.value`、`query.name`、`path.id`、`steps.lookup.0.site_id`、`steps.rows[].value`。入力欄にリクエスト項目と先行処理の参照候補を表示します。「固定値（文字列）」は引用符を付けずに入力でき、「固定値（数値・真偽値・JSON）」では数値`10`、真偽値`false`等を指定します。優先順は未指定/nullを飛ばし、0・false・空文字は保持します。

JSONの構文誤り・処理名の重複・未定義の処理への参照などは、入力内容を確認する際に該当欄へ移動して表示します。「処理の種類」を切り替えて戻すと、その処理で入力済みの内容を復元します（ページの再読み込みやAPIの切替をまたぐ未保存内容の保持ではありません）。

対応する計算は四則演算、四捨五入（HALF_UP）、文字列化、優先順、条件分岐、一致、配列の件数・合計・最小・最大、グループ別集計。複雑な式は複数処理に分け、前の処理を参照します。任意のPythonや無制限の繰り返しをこのフォームで実行する機能ではありません。その他の複雑なSQL・Pythonは既存の拡張方式を使用します。

処理は最大20件、照合は最大30件、DB取得は1回最大5000行。DB参照は読み取り専用です。準備できない場合はAPIを送らず未確認とし、5000行を超えた結果を切り捨てて合格にしません。期待値はAPI実行前に確定します。空の検索結果と空のレスポンスの一致だけでは、検索条件の全分岐を検証したことにはなりません。条件を区別できる試験データは別途用意してください。

日時の組み立て・特殊なJSON成形・高度な優先順位選択には、従来の配列保存設定や期待値SQLも引き続き使えます。未設定の業務ルール、設定した式自体の仕様との一致、未登録の条件は自動では保証しません。未照合一覧でも、ルールを置いただけで全項目のDB照合済みとは扱いません。

## InfluxDB 1.xの一括更新・削除

「InfluxDB：期間・タグで指定した一括変更を照合する」を選びます。POST/PUT/PATCH/DELETEに対応します。

- **確認範囲**：実行前後で全ポイントを比較する期間とタグ条件。開始・終了を両方含む。
- **変更対象**：その範囲内で更新・削除されるべき期間とタグ条件。
- **期待フィールド**：更新の場合、固定値または`point.value`等の実行前の値とリクエスト値から計算する。未指定フィールドは変更なし。
- 削除は対象ポイントの消滅を確認する。

確認範囲に、対象外の時刻・タグを持つポイントも含めてください。範囲内の全タグ・全フィールドを比較し、変更対象の欠落・余分なポイント・値違い・周囲の更新／削除を検出します。範囲外は照合しません。対象外ポイントがない場合は、その維持を確認したことにはなりません。対象0件・更新前後が同じで変更を判定できない場合は未確認です。最大5000ポイント、時刻はナノ秒まで保持します。

このモードは試験データの投入・復旧を行いません。再実行前に検証用DBを元の状態に戻してください。既存の単一ポイント用データ準備・復旧モードは引き続き利用できます。

## 証跡と再検証

Excelの「期待値の作成過程」「期待値ルール照合」「InfluxDB一括照合」に、参照・計算結果、期待値、実測値、判定が残ります。JSONとJUnitも出力します。認証情報や一般的な機密項目は伏字にします。

記録がない詳細シートは作成しません。結果サマリーの「詳細を開く」から、不一致のある照合行へ直接移動できます。HTTP status等で失敗し値の照合自体には不一致がない場合は、DB結果の失敗理由へ移動します。InfluxDBの確認範囲・変更対象・変更前の値は「参考」とし、変更後の比較結果と区別します。DB検索条件は照合シートの詳細欄にも残します。

実DB付き模擬サービスの再検証：

```bash
docker compose -p otg-db-lab -f examples/db-lab/compose.yaml up -d --wait
python docs/run_advanced_db_lab.py --config examples/db-lab/config.json --output .artifacts/advanced-lab
```

出力先は未作成のディレクトリを指定してください。固有名のテーブルとInfluxDBデータベースだけを作成し、終了時に削除します。サービスはlocalhostでのみ待ち受け、期待値エンジンを使わない独立した実装です。検証結果は[検証記録](advanced-db-validation.md)を参照してください。
