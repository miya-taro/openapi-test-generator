# UIでAPIを組み合わせて試験する

「API連携・DB確認」で、複数のAPIを一つの試験にまとめられます。pytestが実行を管理し、HTTPとDBの照合には既存の処理を使います。期待結果は人が指定します。

## 設定手順

1. 「対象を登録」で、呼び出すAPIをすべて登録します。既存OpenAPIの読込みも使えます。
2. 「API連携・DB確認」で本試験のAPIと試験名を選びます。DB照合する場合は通常の対応設定を追加します。APIの応答だけ確認する場合は「DB照合なしのAPI試験を追加」を押します。
3. 登録済み一覧の「APIの連続実行・値の受け渡し・完了待ち」を開きます。
4. 必要な前処理APIを順番に追加します。手順名（例 `create`）、API、送信する項目・型・値、期待ステータス、期待レスポンスの項目を指定します。項目の「送信」を外すと省略です。
5. 本試験の入力で「前のAPIのレスポンス」を選び、「引き継ぐレスポンス項目」の一覧から選択します。OpenAPIに定義のない項目は `create.id` のように手入力もできます。配列は `create.items.0.id`。値は元の型を保持し、文字列への置換は行いません。
6. 非同期処理ならGETの「完了するまで繰り返し確認する」を有効にして、レスポンス項目の一覧から項目（例 `state`）を選び、完了値（例 `done`）、期限、確認間隔を入力します。
7. 必要な後片付けAPIを追加します。`create.id` のほか、本試験が実際に返した値は `result.id` で参照できます。
8. 「連続実行の設定を反映」→「対応設定を保存」→「実行前の確認内容を作る」→内容のレビュー・承認→実行します。

複製・読込みではこれらの設定も保持します。DB照合がなければDB接続設定は不要です。認証は従来のログイン設定・認証プロファイルを使い、全手順に適用します。

## 実行と判定

- 前処理 → 本試験（HTTP・DB照合）→ 後片付けの順です。各手順のHTTPステータスとOpenAPIの応答契約、明示したレスポンス期待値を確認します。
- 前処理が失敗すると残りの前処理と本試験は送信しません。設定した後片付けは失敗時も試み、失敗を合格にしません。
- 前処理で返ったIDをDB条件に使うこともできます。保存形式では `{{steps.create.id}}` です。前の試験の値を自動的に流用しません。
- 完了待ちはGETだけです。各応答の契約を確認し、HTTP不一致・通信失敗・項目欠落では停止します。最大300秒・1,000回で停止し、期限超過は不合格です。POST・PUT・PATCH・DELETEは繰り返しません。
- 前処理を含む一連の流れが一つのpytestケースです。再実行も前処理から実施します。作成APIに副作用がある場合は、後片付けと試験データを定義してください。
- 結果JSONに各送信と応答・待機回数を記録します。結果Excelの「API手順と完了待ち」で手順ごとの期待・実測・判定を確認できます。「送信リクエスト」には前処理・待機中・後片付けを含む各送信のcurlも記録します。
- 強制終了・通信切断時のDBロールバックは保証しません。API側で処理済みでも応答を受け取れなかった場合、生成IDを使う後片付けはできないため、失敗を明示します。

## 範囲

複数DBの参照、優先順位、集計結果の照合は、既存のDB対応・SQLレスポンス照合・共通ルール設定を組み合わせます。API手順に任意のPythonコードを書く必要はありません。複雑な任意の条件分岐・繰り返し、WebSocket、コールバック受信、独自業務計算の自動推測までは対象ではありません。

例は `examples/api-flow/`。実行先に作成・取得・削除APIが必要です。検証では独立したHTTPサーバーとPostgreSQLを用い、正常完了だけでなく、途中失敗・返却値不一致・期限超過・後片付け失敗を確認しています。

## 入力中の案内

参照先が削除された場合・後ろの手順を参照した場合・ステータスや待ち時間が不正な場合は、設定欄の下に理由を表示し、反映を止めます。これは設定形式の確認です。APIの正しさや試験の網羅性の保証ではありません。必須項目を省略する異常試験は設定できます。

レスポンス項目の候補は登録したOpenAPIの成功レスポンス定義から表示します。前処理ではそれ以前の手順、本試験では前処理、後片付けでは本試験（`result`）とそれ以前の手順を選べます。配列の `.0` は先頭要素です。配列全体・オブジェクト全体もその型を保持して受け渡せます。

## ログインの設定

「4. 実行」→「詳細設定（認証・DB・実行方法）」で「ログイン認証を行う」を有効にし、ログインAPIを選択します。

- 登録済み項目の入力欄に、実際にログインできる試験用アカウントを入力します。パスワード欄は伏字です。
- 今回のAPIは「id → auth-key」を選ぶと、レスポンスの `id` をヘッダ `auth-key` に送る設定になります。Bearer方式には別のテンプレートを用意しています。方式は人が仕様に合わせて選びます。
- 認証に使うレスポンス項目も一覧から選べます。独自のヘッダ名・値の形式・項目パスは編集できます。
- 入れ子などの詳細設定は「ログインボディをJSONで編集」を使用できます。通常の設定保存には認証ボディを保存せず、再起動後は再入力します。「ファイルに保存」は認証情報を含む明示的なエクスポートです。
