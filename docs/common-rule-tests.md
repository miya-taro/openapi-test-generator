# UIで作る共通ルールの試験

「DB確認」の登録済み設定を開き、**共通ルールから試験を作成**を使います。
APIの仕様・正常な送信値・DBとの関係は人が設定します。ツールはその設定をケースに展開し、HTTP送信・照合・証跡保存を実行します。

## 操作

1. 基準になるAPI・正常リクエスト・DB対応を登録します。既存設定は「選択したDB確認ファイルを編集用に読み込む」で開けます。
2. 登録済み設定の「共通ルールから試験を作成」を開き、試験の種類を選びます。
3. 下表のルールと、必要な検証データを入力します。
4. 「生成する試験を確認」で、各ケースの送信値・準備する行・期待結果を確認します。まだAPIは送信されません。
5. 「確認した試験を追加」→「対応設定を保存」。不要な基準ケースは削除してから保存できます。
6. 実行前の確認を準備し、内容をレビュー・承認して実行します。結果ExcelとJSON証跡に判定が残ります。

設定を編集するとプレビューからやり直します。保存後に読み直してもルール入力を復元できます。
レビュー／承認の保存中は、他ケースのレビュー操作も停止し、保存の競合を防ぎます。

## 人が指定することと自動で作るケース

| 種類 | 人が設定すること | 自動生成する試験 |
|---|---|---|
| 期間の境界 | 開始・終了の入力項目、DB日時列、各境界を含むか、刻み幅 | 開始の直前・一致・直後／終了の直前・一致・直後の6件 |
| 項目の組み合わせ | 項目ごとの正常な候補値・省略するか・項目間の必須条件・正常／異常status | 候補値と省略の全組み合わせ。少なくとも一方必須、両方指定／両方省略、どちらか一方だけ必須を判定 |
| データの優先順位 | 優先する順番で候補行を2〜8行、基準行から変える列 | 全ペアを2通りの投入順で確認。3行以上なら全候補の順方向／逆方向も確認 |
| 対象データ0件 | 期待statusと、空配列・固定レスポンス値・本文なしのいずれか | 対象範囲が0件のとき、明示された応答になるか確認。200／400などを推測しない |

期間境界・優先順位・0件の共通生成はGETに対応します。組み合わせは他メソッドでも使えます。
組み合わせの対象はボディ直下・query・pathの文字列／整数／数値／真偽値、最大6項目です。
**64件を超える場合は一部を黙って省略せず停止**します。条件を分けて設定してください。
候補値は正常値を入力します。合成schemaや入れ子項目の組み合わせは個別ケースで設定します。
パス項目は省略できません。query・pathのnullは送信値にせず、省略候補として設定します。
DB確認のHTTP送信では真偽値を`true`／`false`に統一し、パス値をURLエンコードします。
共通ルールでJSON項目をすべて省略した場合も、空オブジェクト`{}`と本文なしを取り違えず送信します。
認証、既存のDB照合、契約の型・必須・境界値試験は従来の機能と併用します。

## 検証データ

専用のテストDBを使います。PostgreSQLまたはInfluxDB 1.xで、1テーブル／measurementの専用範囲を指定します。

- PostgreSQL: 範囲の列名と固定値、初期行の各列・型・値。実テーブルに主キーが必要です。採番列は省略できます。
- InfluxDB: 範囲には全タグを文字列で指定。初期行は`time`とフィールドの型・値を指定します。
- 準備前に範囲が空であることを確認します。既存データ・列不備・主キー衝突等があればHTTPを送らず「未確認」で止めます。
- 終了時は投入した主キー／時刻・全タグの行だけを片付けます。別拠点の行は削除しません。
- 作成した行以外のデータが専用範囲に残ったときや片付けが失敗したときは合格にしません。証跡を確認して対処してください。
- 同じ範囲へ別の利用者・バッチが書き込む環境は使わないでください。複数DBをまたぐ一括トランザクション、APIが主キー・タグを変えて範囲外へ移した行の自動追跡／削除、強制終了後の自動復元は対象外です。

期間では期間内の基準行と境界の確認行の2行を準備します。
優先順位では同じ選択グループに属し、主キー／時刻が衝突しない候補を入力してください。

両機能は、人が指定した「そのままレスポンスに返る数値列」に1、2…を入れて行を識別します。
指定配列を展開し、順序を無視して**値・件数・欠落・余分な行・重複**を比較します。
他の列まで自動的に照合したことにはなりません。既存のDB対応・SQL対応で補います。

組み合わせの異常系では、DB変更なしを確認する範囲が必要です。複数範囲を追加でき、InfluxDBでは固定期間も指定します。

## 対応範囲の表示

実行前の「仕様の対応状況」に、共通ルールの登録条件と対応する試験IDを表示します。
ケース未設定のルールは、仕様上必要か人が確認する項目として表示します。
**「照合設定あり」は合格や全条件の網羅を意味しません。** 実行結果と仕様全体の網羅性は別です。

複雑な優先順位の仕様そのもの、SQLの正しさ、他テーブルへの副作用、非同期処理、同時実行、性能・大量データの十分性は、この生成だけでは保証しません。

## 検証

`runner/tests/test_rule_cases.py`はUIと同じ生成処理からケースを作り、独立したローカルHTTP APIと実PostgreSQL／InfluxDBで検証します。
正常APIに加え、境界除外／包含の誤り、優先順位逆転、返却行の欠落・重複・値違い、条件違反の受付、0件時のstatus違いを検出します。
再実行、既存データがある範囲での停止、別拠点データの保護、準備失敗、余分な残留行の検知も確認します。

`gui/tests/test_browser_rule_cases.py`は4種類のルールについて、ブラウザでプレビュー・追加・保存・再読込・レビュー・実行・Excel取得まで確認します。
これらは専用の検証APIでの確認です。利用先の業務APIで実行済みという意味ではありません。

### 2026-10-13の実行結果

- PostgreSQLとInfluxDBで各72回のHTTP試験（正常API64回、故障API8回）。正常はすべて合格、8種類の故障はすべて不合格として検出。
- 上記とは別に、既存行がある範囲・存在しない列・主キー衝突でのHTTP未送信と、残留行を黙って削除しないことを確認。
- ブラウザ4フロー合格。期間6件・優先順位8件・0件1件・組み合わせ16件を保存し、読み直して実行、Excelを取得。
- フロントエンドの144テスト、Lint、ブラウザ用ビルドが成功。
- DBシナリオ／レスポンス照合／HTTP周辺184テスト、ワークフロー85テストが成功（追加の環境が必要な4テストはスキップ）。

再現用のテストとCIジョブをリポジトリに追加しています。Windowsインストーラーの再ビルド・業務APIへの接続確認はこの検証には含みません。
