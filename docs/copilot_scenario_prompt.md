# DBシナリオ候補 生成プロンプト（GitHub Copilot Chat用）

`runner/db_scenario_runner.py`（Layer2）のシナリオYAML（`given`/`request`/`db_check`/
`response_check`）は、スキーマの制約（`minLength`や`enum`等）からは絶対に導出できない
「業務ルール」を検証するためのもの。この種のルールは、そもそも人間が「このAPIには
こういう業務上の制約があるはずだ」と気づかない限り、テストケースとして存在すらしない。

このプロンプトは、Copilot Chatに openapi.json・既存のシナリオYAML・実装コードを
読ませて、**見落としがちな業務ルールのテスト候補を提案させる**ためのもの。
提案されたものは全て人間がレビューしてから実際の `scenarios.yaml` に追加する
（Copilotに直接YAMLファイルを編集させない）。

## 使い方

1. VS CodeでこのプロジェクトのCopilot Chatを開く
2. 対象APIの `openapi.json`、既存の `scenarios.yaml`（あれば）、業務ロジックの実装ファイルを
   エディタで開いておく（Copilotが `#file` で参照できるようにするため。無くても動くが精度が落ちる）
3. 下記「プロンプト本体」をそのままCopilot Chatに貼り付ける（`openapi.json`のパス等、
   `<...>` の部分は実際の値に置き換える）
4. 出力された候補を人間がレビューし、妥当なものだけ `scenarios.yaml` に手で追加する

Tauri版GUIの「DB準備」→「3. DB検証シナリオを生成」にある折りたたみ欄から、
選択済みファイルのパスを差し込んだ依頼文をコピーできます。Copilot Chatがそのパスを
直接読めない場合は、対象ファイルを開いて `#file` で参照するか、チャットへ添付してください。

## プロンプト本体（ここから下をコピー）

```
あなたはAPIの試験設計者です。以下の入力から、スキーマの制約（型・必須・enum・桁数等）
だけでは絶対に見つからない「業務ルール」のテストシナリオ候補を提案してください。
スキーマの制約から機械的に導出できる境界値・異常系テストは既に別のツール
（openapi-test-gen の Layer1）でカバー済みなので、ここでは提案しないでください。

# 入力
- OpenAPI定義: <openapi.jsonのパスを指定、またはファイルを添付>
- 既存のDBシナリオYAML: <scenarios.yamlのパスを指定。無ければ省略可>
- 業務ロジックの実装: <可能であれば、値の計算・状態遷移・権限チェックをしている
  ソースファイルを指定。無ければ省略可>
- DBスキーマ: <schema.sqlやマイグレーションファイル等があれば指定。無ければ省略可>

# 探してほしい業務ルールの種類
以下の観点で、このAPIに存在しそうな（が、スキーマには明示されていない）業務ルールを探してください。
全部に該当例が無くても構いません。無理に候補をひねり出さないでください。

1. **状態遷移ルール**: 特定の状態からしか遷移できない/できない操作
   （例: キャンセル済みの注文を発送できてはいけない）
2. **不変条件・保存則**: 複数の値の間で常に成立すべき関係
   （例: 注文明細の合計金額 = 各明細の小計の合計）
3. **一意性制約**: DBのUNIQUE制約には現れない、業務レベルでの一意性
   （例: 同じクーポンコードは同一ユーザーに対して1回しか使えない）
4. **認可・所有権**: 他人のリソースを操作できてしまわないか
   （例: ユーザーAがユーザーBの注文を取得・更新・削除できてしまう）
5. **時系列・順序制約**: 日時やイベントの順序に関する制約
   （例: 終了日は開始日より後でなければならない、支払い前の返金はできない）
6. **カスケード影響**: あるリソースの変更が関連リソースに正しく波及するか
   （例: 商品を削除したら、それを含む未処理カートからも正しく除外される）
7. **冪等性**: 同じリクエストを複数回送っても、意図しない多重処理が起きないか
   （例: 決済確定APIを2回叩いても二重に引き落とされない）
8. **業務固有の境界ルール**: スキーマの `minimum`/`maximum` 等では表現できない、
   ドメイン固有の制約（例: 在庫予約は15分で失効する、割引は税抜金額に対してのみ適用される）
9. **単発の入力注入耐性**: SQLインジェクション、反射型XSS、パストラバーサルについて、
   実装上その入力が使われる箇所を特定でき、開発環境で1リクエストだけ実行できる場合に限り、
   無害な代表文字列を使った候補を提案する。破壊的なSQL、遅延・大量データを発生させる入力、
   外部ファイルへの書込み、OSコマンド実行につながる入力は提案しない。

# 出力形式
候補ごとに、以下の形式で出力してください（このツール独自のYAML DSLです）。

  - name: <シナリオの名前。何を確認するテストか一目で分かるように>
    観点: <どんな業務ルールを、なぜ検証すべきなのか（レビューする人が判断できる理由）>
    given:                          # 前提データが必要な場合のみ（無ければ省略）
      - table: <テーブル名>
        as: <このシナリオ内で参照する名前>
        fields: { <カラム名>: <値> }
    request:
      operationId: <openapi.json に実在する operationId>
      path_params: { <パラメータ名>: "{{given.<as名>.<カラム名>}}" }
      body: { <フィールド名>: <値または "{{given.<as名>.<カラム名>}}"> }
    auth_profile: <GUIの役割別ログイン情報で定義した名前。通常ログインなら省略>
    db_check:                       # DB状態の検証が必要な場合
      table: <テーブル名>
      where: { <カラム名>: <値> }
      expect: { columns: { <カラム名>: <期待する絶対値> } }
      invariants:                   # 絶対値ではなく関係式で検証したい場合
        - "{{db.<カラム名>}} == <前提データや直前レスポンスを使った式>"
    response_check:                 # APIレスポンス自体を検証したい場合
      expect: { status: <期待ステータス>, body: { <フィールド>: <期待値> } }

# 厳守してほしいこと
- `operationId` は必ず入力の openapi.json に実在するものだけを使う。存在しないものを
  作らないこと。判断に必要な情報が入力に無い場合は、無理に埋めず
  「情報不足のため要確認: 〇〇」と明記すること
- `table`/カラム名も、入力のDBスキーマ・既存シナリオYAMLに実在するものだけを使う。
  推測でカラム名を作らないこと
- あなたはこのファイルを直接編集しません。候補を提示するだけにしてください
  （人間がレビューしてから scenarios.yaml に反映します）
- 1つの業務ルールにつき1シナリオ。欲張って1シナリオに複数の観点を詰め込まないこと
- 認可シナリオは `auth_profile` に実在する試験アカウントの役割名を指定する。役割別ログイン情報が未定義なら必要な設定名だけを示し、認証情報そのものをYAMLへ書かない
- 所有権試験では、試験ログインユーザーとは別のユーザーが所有する `given` データを作る。`given` の後続項目は `{{given.<as名>.<カラム名>}}` で先行データを参照できる。拒否レスポンスに加え、DB状態が変わっていないことも確認する
- 注入耐性候補は対象フィールド・使う文字列・根拠となる実装箇所・安全性の理由・期待レスポンス/DB状態を併記する。仕様から期待値を確定できない場合は試験ケースを捏造せず「要確認」とする
- 注入耐性は人がレビューした単発ケースだけを候補にする。大量試行、総当たり、遅延ペイロード、広範なID列挙、データ破壊につながる入力は除外する
```
