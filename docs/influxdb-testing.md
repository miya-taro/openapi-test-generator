# InfluxDB 1.xをUIから照合する

対応対象DBはPostgreSQLと **InfluxDB 1.x（InfluxQL）** です。MySQL／SQL ServerおよびInfluxDB 2.x／3.xは今回の対象外です。

## GETレスポンスを期間内の全ポイントと比較

1. OpenAPIを読み込み、詳細設定で「InfluxDBを使う」を選び、host・port・databaseと必要な認証情報を入力。
2. 「DB確認」でGET操作を選び、確認するDBを「InfluxDB 1.x」にする。
3. テーブル / measurement欄に対象measurementを入力。
4. 検索項目に、送信する値、DBのtime・タグ・フィールド名、比較演算子を入力。
5. レスポンス項目に対応するDB項目を入力して、対応設定を追加・保存。
6. ケースを準備し、確認・承認して実行。結果Excel・比較証跡から期待ポイントと実際の応答を確認。

例：`/v1/result/measure/get`（GET・JSON body）

| API入力 | InfluxDB項目 | 比較 |
|---|---|---|
| site_id | site（整数フィールド） | =、location_idと同じORグループ |
| location_id | location（タグ） | =、site_idと同じORグループ |
| start | time | >=（仕様が開始を含む場合） |
| end | time | <=（仕様が終了を含む場合） |
| items | item（タグ） | IN |

`result[].time → time`、`result[].item → item`、`result[].value → value`を対応付けます。
レスポンスの順序は問いませんが、件数・各値・重複数まで比較します。timeはタイムゾーンの違いを吸収し、ナノ秒の差は保持します。

Bodyの値は利用者が指定します。条件付き必須とIN配列の組み合わせ生成はPostgreSQLと共通です。
Query / Pathの値は、従来のDB対応画面と同様、明示されたDB列の既存データから境界確認用の値を選びます。対応列や仕様そのものは推測しません。

条件を外したときに増えるポイント、開始終了の境界、各IN要素、各OR分岐を識別できる既存ポイントが必要です。十分なデータがなければHTTP送信前に「未確認」とし、合格にはしません。試験データの自動投入はありません。

## API実行前後で変更がないことを確認

「DB確認」で、確認する内容を「API実行前後でDBに変更がないこと」にします。
InfluxDBでは、measurement・比較する項目・等値条件に加え、タイムゾーン付きの固定開始／終了日時（両端を含む）を入力します。
`now() - 5m`のように実行中に動く範囲は使わず、前後で同じ期間を比較します。

比較項目には `time` とポイントを識別する全タグも含めてください。指定しない項目は比較しません。
GET / POST / PUT / PATCH / DELETEで利用できます。POST等の成功時に変更が必要なことを判定するモードではありません。

通常の契約試験で、自動生成する異常系すべてに前後比較を付ける場合は、契約編集の「自動生成する異常系でDBが変わらないことを確認」に同じ範囲を設定します。OpenAPIへの保存形式は次の通りです。

```json
"x-otg-error-db-unchanged": [{
  "engine": "influxdb",
  "table": "measure",
  "columns": ["time", "location", "item", "value"],
  "where": {},
  "time_start": "2026-01-01T00:00:00Z",
  "time_end": "2026-01-02T00:00:00Z"
}]
```

InfluxDBだけの接続設定でも実行できます。異常系の前後ポイントは `test-result-db-evidence.json`、個別DB確認の証跡は通常のDB比較エビデンスに残ります。

## POST / PUT / PATCH / DELETEの保存・更新・削除

「DB確認」でAPI操作とInfluxDBを選択し、次を設定します。SQLやInfluxQLを書く必要はありません。

1. measurementと、確認する処理（新規保存／更新／削除）を選ぶ。HTTPメソッドによる初期値は変更できます。
2. 対象ポイントの固定時刻と**全タグ**を指定する。これが実行前後で照合する1ポイントの識別条件です。
3. POST / PUT / PATCHは、表示されたリクエスト項目に送信値と保存先フィールドを入力する。保存値の変換は画面で明示したものだけを使います。DELETEでボディが必要なら専用欄へJSONを入力します。
4. 期待する成功ステータスを指定する。更新時は「未指定フィールドの値を維持」も確認できます。
5. 追加・保存→ケース準備→内容の確認・承認→実行。前後ポイント・期待フィールド・件数・判定をExcelとJSONに保存します。

| 処理 | 実行前 | 合格となる実行後 |
|---|---|---|
| 新規保存 | 対象ポイントがない | 対象が1件になり、指定した全フィールドが期待値と一致 |
| 更新 | 対象が1件あり、少なくとも1つの期待値と異なる | 対象が1件で、指定した全フィールドが期待値と一致 |
| 削除 | 対象が1件ある | 対象が0件 |

前提が満たされない場合は「未確認」としてHTTP送信前に停止します。例えば、既に期待値と同じデータを更新する試験を合格にはしません。既定ではポイントの投入・後片付けを行わず、既存データを使います。同じ設定で繰り返す場合は、次の検証用ポイント設定を利用できます。

### 同じ試験を繰り返すための検証用ポイント

「検証用ポイントを毎回準備し、試験後に削除する」を有効にします。

- 上のポイント時刻と全タグを検証専用として指定します。対象に既存ポイントがある場合は**上書きもHTTP送信もせず未確認**で停止します。
- 新規保存では初期ポイントを投入せず、APIが作成した対象ポイントを試験後に削除します。
- 更新・削除では「初期フィールドを追加」から名前・InfluxDB型・初期値を入力します。型はstring／integer／float／booleanを選びます。既存measurementのフィールド型に合わせてください。更新の初期値が期待値と同じなら、投入・HTTP送信前に停止します。
- 実行時に初期ポイントを投入・読取確認し、その後APIを実行して結果を照合します。ケースを準備・レビューするだけでは投入しません。
- 成功・不合格・API通信エラー・投入応答の取得失敗でも、確保した対象ポイントの削除を試みます。準備・後片付けの状態は `db-scenario-evidence.json` の `influx_fixture` に残ります。後片付けに失敗したケースはNGになり、Excelにも表示します。
- 正常に片付けば、同じ設定・同じ時刻・タグで再実行できます。内容を変えない再準備では既存の承認状態を利用できます。初期値や自動準備設定を変えるとケースIDが変わり、再確認が必要です。

削除対象は指定時刻＋全タグの1ポイントのみです。別時刻・別タグのポイント、APIが誤って作った別ポイント、measurementのフィールド定義は削除しません。既存データの復旧機能ではありません。同じ対象に他の処理が書き込まない検証環境で実行してください。強制終了・電源断時の自動復旧はありません。残ったポイントは確認してから片付けてください。

保存される設定例（更新）：

```yaml
influx_mutation:
  measurement: measure
  time: '2026-01-01T00:00:00Z'
  tags: {item: a}
  action: update
  fields: {value: 2.0}
  fixture:
    fields:
      value: {type: float, value: 1.0}
```

初版は固定時刻＋全タグで特定する**単一ポイント**が対象です。サーバー採番時刻の取得、期間内の一括変更、タグ構成の異なる系列が混在するmeasurementは対象外です。別ポイントへの余分な変更まで確認するには、別途「DB変更なし」の範囲設定が必要です。

## 対応範囲と制限

- 1回の照合上限は5,000ポイント。上限を超えて切り捨てた結果を合格にしません。Query / Pathの自動値選択元も同じ上限です。
- 未定義のmeasurement・項目、未取得・接続失敗、条件確認用データ不足は合格にしません。
- 行条件のnullは非対応。タグは文字列、timeはタイムゾーン付き日時で指定します。型変換・集計・JOINは行いません。
- 前後比較は他の書き込みがない検証用範囲で実行してください。非同期反映待ち・既存DBの復旧はありません。ポイント投入／後片付けは、上記の変更確認で明示した検証用ポイントのみです。GET用データの自動投入はありません。
- GETの全ポイント照合と、POST／PUT／PATCH／DELETEの単一ポイント変更をUIから設定できます。既存YAMLの最新1ポイント検証も従来どおり利用可能です。
- PostgreSQL設定の既定値と既存ファイル形式は維持します。

## 検証（2026-10-12 日本時間）

実InfluxDB **1.8.10** と独立したHTTP APIを使い、UIの生成関数から出力した設定をCLIで実行しました。

- 正常な条件組み合わせ18件、順序逆転、同じ時刻を異なるタイムゾーンで返すAPIが合格。
- 条件無視・OR→AND・境界除外・IN先頭だけ・欠落・重複・値違い・1ns違いの12種類を不合格として検出。
- 条件確認用データが不足した場合は「未確認」、HTTP未送信。
- 5メソッドの前後変更なし確認が合格。
- 自動生成異常系20件がDB変更なしで合格。更新・挿入・削除を起こす同じ20件×3種の計60件を不合格として検出。
- 実Chromiumで、UIからGET対応を入力→18件生成→保存、異常系比較範囲を設定→OpenAPI保存→再読込を確認。
- 全117 HTTP呼び出し。ExcelとJSON証跡を出力。利用者の実API・実DBは未検証。
- 保存・更新・削除を追加検証：4メソッドの正常系が合格。未実行・別ポイント変更・値違い・未指定フィールド破壊の計13ケースを不合格として検出。前提不足4ケースはHTTP未送信。計17 HTTP呼び出し。
- 実Chromiumで、POSTのDB対応を入力→保存→ケース準備→レビュー・承認→実API実行→実InfluxDBの値を確認→合格結果Excelのダウンロードまで成功。
- 検証用ポイントを有効にして4メソッド×2回を手動のデータ再投入なしで成功。APIが処理しない4ケースはNGを検出し、後片付けも成功。既存データ衝突4ケースはHTTP未送信・既存ポイント維持。同時刻の別タグ・同タグの別時刻のポイントが残ることも確認。
- 初期ポイントのナノ秒時刻を維持し、隣接する1ns前のポイントを削除しないことを実DBで確認。投入応答喪失・API通信エラー・後片付け失敗の単体試験、実Chromiumからの2回連続実行とExcel取得も確認。

再現するには検証用InfluxDBを起動し、次の環境変数で結合試験を実行します。試験は一意な専用databaseを作成して最後に削除します。

```bash
OTG_INFLUX_INTEGRATION_CONFIG='{"host":"127.0.0.1","port":8086}' \
OTG_INFLUX_EVIDENCE_DIR=/tmp/influx-evidence \
python -m pytest runner/tests/test_influx_response_e2e.py runner/tests/test_influx_mutation_e2e.py -q
```
