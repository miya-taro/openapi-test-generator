# GET JSONボディの測定結果検索

検証例のOpenAPIは [measure-get-openapi.json](../examples/measure-get-openapi.json)。
これは `/v1/result/measure/get` の試験用の仕様であり、実際のAPIの業務上の期待結果を決めるものではない。
例では拠点IDを両方送った場合はOR、期間は両端を含む、検索結果0件も200としている。
実際の仕様に合わせてUIの比較条件・ORグループ・期待statusを設定する。

## 画面で設定する内容

1. 契約UIでGET、JSONボディとレスポンスを定義するか、OpenAPIを読み込む。
2. リクエスト項目の必須条件に `site_id` / `location_id` の「どちらか必須」、
   `start` / `end` の「両方指定または両方省略」を追加する。`items` は個別に必須。
3. DB確認で対象のPostgreSQLテーブルと次の対応を入力する。

| API入力 | DB列（例） | 比較条件 | ORグループ（両拠点IDがORの仕様の場合） |
| --- | --- | --- | --- |
| site_id | site_id | と等しい | A |
| location_id | location_id | と等しい | A |
| start | measured_at | 以上 | AND |
| end | measured_at | 以下 | AND |
| items | item_name | 配列に含まれる | AND |

4. レスポンスの配列パスを `result` として、`time` → `measured_at`、`item` → `item_name`、
   `value` → `measured_value` を設定する。DB照合はこれらの値と件数を比較し、順番は問わない。
5. 各Body項目へ人がDBにある試験値を入力する。「条件付き必須とIN配列の正常な組み合わせを生成する」を選ぶ。
   `items` に2種類入力すると、拠点3通り × 期間2通り × items3通りの18ケースを追加する。
   配列の `minItems` が2以上の場合は1項目だけの正常ケースを作らない。展開は最大64件。
6. 「レスポンス項目の値の照合」で、配列外の `site_id` / `start` / `end` の期待値を設定する。
   同じ名前の送信値を返す仕様なら「送信値と一致」を選び、照合元のBody項目を選ぶ。
   組み合わせには入力を省略するケースもあるため、仕様に応じて「省略時は固定値」を選んで期待値を入力する。
   省略時の値照合が不要なら「指定時のみ」を明示する。仕様が決まっていなければ既定の「型・形式のみ」を使う。
7. 追加されたリクエストと照合設定を確認して保存し、通常の準備・レビュー・実行の手順へ進む。

組み合わせの期待statusは入力した値を共通で使う。組み合わせごとに別statusになる業務仕様は、
組み合わせ生成を外して個別に設定する。開始・終了の大小関係や空配列を拒否するかも推測しない。

## 追加で指定できる確認

仕様が `start <= end` なら、契約画面の「項目間の大小条件」で定義し、大小・同値の3ケースを生成できる。
参照APIやエラー時のDB変更なしは、DB確認画面で比較する範囲・列・送信値・期待statusを指定する。
手順と制限は [項目間条件・DBの変更なし確認](comparison-and-side-effects.md) を参照。

## 合格にするための確認

- 日時の形式・型を試すリクエストでは、相方の日時項目を補い、条件付き必須による別のエラーを避ける。
  条件付き必須自体を破る専用ケースでは、その不正な組み合わせを保持する。
- 検索条件を外した場合に結果が変わるDB行があることを、条件ごとに確認する。
- ORではグループの条件漏れだけでなく、各分岐だけで一致するDB行があるかも確認する。
- 期間は設定した開始・終了値ちょうどの行があるか確認する。`>` / `<` を選んだ場合も端点の除外を確認できる。
- INは各指定値に一致する行があるか確認する。
- 上記の行がなく不具合を区別できない場合、HTTP送信前に「未確認」（終了コード2）を返す。
  ツールが自動で本番DBへ試験データを追加することはない。
- 同じAPI応答について、契約試験と共通の処理でOpenAPIの型・必須項目・`date-time`などの形式、
  Content-Typeとヘッダschemaを検証する。DB対応のないルートの `site_id` / `start` / `end` も型・形式は検証する。
  リクエスト値との一致を業務上の期待値として自動で仮定することはない。
- 人が設定した値照合は、各ケースで実際に送信したBody/Query/Pathの値、または指定した固定値と比較する。
  日時はタイムゾーン・小数秒の表記が異なっても同じ時刻なら一致し、小数秒の差も検出する。
  省略時の期待値は人の設定に従う。省略時に照合しない設定は証跡に「対象外」として残し、確認済みと混同しない。

検証用APIでは、`site_id` を省略したときの値を `2`、期間を省略したときの値を
`2026-01-01T00:00:00Z` / `2026-01-03T00:00:00Z` と定義している。この例の値を実APIへ流用しない。
実APIが別の値を返す場合はその期待値を入力し、組み合わせごとに変わる場合は個別設定を使う。

DB照合の期待値・実測値・条件を確かめる行の有無・契約検証・レスポンス値照合の判定は `db-scenario-evidence.json` に残る。
この例は単一テーブルの行照合。location_idから別DBのsite_idを取得して絞り込む場合は[別DB参照](cross-db-lookup.md)を設定できます。任意JOIN、集計、ページング、大量データ・性能試験はこの方式には含まれません。

## 再現できる実API・DB検証

開発用依存をインストールし、検証専用のPostgreSQLへの接続設定を
`OTG_INTEGRATION_DB_CONFIG` にJSONとして設定する。テストは専用の一意な名前のテーブルだけを作成・削除する。

```sh
python -m pytest runner/tests/test_measure_get_e2e.py -q -s
```

検証ではUIの実際の生成処理から設定を作り、GETのJSONボディをHTTPで送信する。
正常な検索を照合するほか、検索条件漏れ、ORの取り違え、期間の端点誤り、
値の改変、ルート項目・ヘッダ・日時形式の違反、不正JSONを持つAPIをNGにできるか確認する。
ルートの `site_id` / `start` / `end` を型・形式が正しい別の値にしたAPIも不合格にし、
同じ時刻を別のタイムゾーンで返す正常なAPIは合格することを確認する。
同じAPIで、生成した契約試験も実行する。

`OTG_MEASURE_EVIDENCE_DIR` を指定するとJSON比較証跡・UI生成YAML・契約試験Excelをそのフォルダーへ保存する。
CIでも実行し、`measure-get-evidence` 成果物へ保存する。

日時検証の依存ライブラリ `rfc3339-validator` はMITライセンス。`requirements-runtime.txt` に含まれ、
ローカル起動とWindows用パッケージの共通依存としてインストールされる。
