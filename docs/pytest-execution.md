# 実行基盤と独自機能の分担

完成形の目的は、既存エンジンを作り直すことではなく、API仕様・正常値・DB対応を人がUIで設定し、試験コードを書かずに実行と証跡確認まで進めること。

| 責務 | 使用するもの |
|---|---|
| ケース単位の実行、fixture、停止、JUnit | pytest |
| 独立した契約ケースの並列実行 | pytest-xdist（ワーカープロセスごとにSessionを分離） |
| HTTP通信 | requests |
| JSON Schema照合 | jsonschemaと形式検証ライブラリ |
| PostgreSQL / InfluxDB 1.x接続 | psycopg2 / influxdb |
| APIとDBの対応設定、条件別ケースの生成、保存値・返却値の比較、未照合の表示 | このツールのドメイン処理 |
| UI、Excel、HTML | 定義・結果を表示するための入出力 |

pytest単体にAPIケースの自動生成やDB期待値の推測を任せているわけではない。業務上の正解は人が定義する。Karateでもコードや設定を書けば同種の試験は可能だが、このツールでは対象範囲の定義をUIで作れることを価値とする。

## 実装した実行契約

- UIとworkflow CLIの契約試験・DB試験は `runner/pytest_runner.py` に統一。
- `case-master.json` に、解決済みOpenAPIと実行ケースを保存する。ケースの定義ハッシュにレスポンス契約も含め、DB試験も契約変更後は再確認が必要。
- 実行開始時に定義を検証し、その実行専用の一時スナップショットを作る。実行中に元のOpenAPI・YAML・Excelを読み直して送信内容を変更しない。
- 固定の `runtime_suite.py` をpytestでパラメーター化する。ケースごとのPythonコード生成は行わない。
- `runtime_service.py` がHTTP・DB照合を行う。Sessionと認証状態の取得・解放はpytestのsession fixtureが管理する。設定と結果の変換は `execution_plan.py` とランナーの出力処理が担当する。
- Excelは入力として読まない。実行時にJSON定義からレポート用の仕様Excelを作る。Excelの編集は送信内容・判定に影響しない。
- 結果Excelと同じ名前の `.json` に、ケースID、定義ハッシュ、判定、実測値、照合証跡を保存する。JUnitはpytestが出力し、未開始ケースと実行全体のエラーを追記する。

## 状態・副作用

- 合格、不合格、実行エラー、未確認、未実施を分ける。0ケースの実行を成功にしない。
- ログインやfixtureの準備に失敗した場合は、その試験を合格にしない。機密情報を含み得る例外本文やローカル変数は出力しない。
- 逐次実行ではCookie維持と直前レスポンス参照を維持する。DB照合・DB変更なし確認は逐次実行限定。
- 並列実行ではSessionを共有しない。ログインが必要ならワーカーごとにログインする。並列実行を指定する人は、各リクエストが同じデータを取り合わないことを確認する。
- 明示したGETの完了待ちを除き、自動再試行は行わない。並列ワーカーが落ちた場合も自動再起動しない。書込みAPIの二重実行を避ける。
- 契約試験の実行前後SQLは全体で一度ずつ。準備SQLが途中失敗しても、指定された後片付けSQLを試みる。後片付け失敗は実行エラーとしてJSON・JUnit・Excelへ残す。
- fail-fastで未開始になったケースは未実施。OSによる強制終了などでは後片付けを保証できない。
- 起動環境のpytest設定や自動ロードされた外部プラグインで、勝手に試験対象・実行条件を変えない。

## 移行範囲

UIの設定形式と試験ID、既存のDB対応・比較ルールは維持する。更新後はケースを一度再準備する。追加依存は起動時のrequirements更新で導入する。

従来の `runner.py`（Excel入力）と `db_scenario_runner.py`（YAML入力）は旧CLI利用者向けの互換入口として残すが、UI/workflowの実行経路には使わない。DB照合のドメイン関数は再利用する。すべての内部モジュールの移動や旧CLIの削除まで済んだという意味ではない。

Schemathesisの探索試験は独立した補助機能として維持する。任意の業務ロジック、負荷試験、全APIの自動網羅を保証するものではない。

## 今回の検証

- 新経路で249件の生成契約ケースを実HTTP実行し、GET・POST・PUT・PATCH・DELETEの成功と故障時のNGを確認。
- ログイン付きの計画POST・計画GET・pwrco POSTを、独立した検証APIとPostgreSQLで実行。正常ケースの成功と、保存値・返却値の故障検出を確認。
- Chromiumからの保存・承認・実行・ダウンロードも確認。PostgreSQL・InfluxDBを含むGUI試験120件が成功。
- ランナー全1,009件、生成処理270件、workflow 87件が成功。workflowの探索試験関連4件はこの回帰実行ではスキップ。
- 並列実行、fail-fast、定義改変、Excel破損、元ファイル削除、認証失敗、準備・後片付け失敗、他のpytest設定の混入防止も検証。

これは検証用API・DBでの結果であり、利用者の実システムへ接続して確認した結果ではない。Windowsの回帰・起動確認はGitHub Actionsでも行う。

UIでのAPI連続実行・レスポンス値の受け渡し・完了待ちは [API手順の設定](api-flows.md) を参照してください。
