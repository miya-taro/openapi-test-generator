# GETの期待値SQLと入れ子レスポンスの照合

DB確認 → 確認する内容 → **GET：SQL取得結果と入れ子レスポンスを照合する**。
PostgreSQLのJOIN・CTE・ウィンドウ関数などで期待する行を取得し、入れ子JSONと比較する機能です。InfluxDBへの任意SQL実行は対象外です。既存の契約試験（型・必須・入力制約）は併用します。

## 設定手順

1. OpenAPIを読み込み、対象GET操作とPostgreSQL接続を選択します。
2. 期待値取得SQLを入力します。結果の列は一意の別名にします。単一のSELECTまたはWITH文が利用できます。SQL中のセミコロンは末尾以外使用できません。
3. 「SQLパラメータを追加」で名前、リクエストの入力場所（body/query/path）、項目パス、省略時の扱いを指定します。SQLには `%(site_id)s` のように書きます。引用符で囲む必要はありません。リクエスト値はpsycopg2のパラメータとして渡し、SQL文字列に連結しません。名前は英数字とアンダースコアです。SQLのリテラル `%` は `%%` と記述してください。
4. JSON bodyや既存のクエリ・パス欄に送信値を入力します。GETのJSON bodyにも対応します。省略時NULLを選ぶと、項目がない場合にSQLへNULLを渡します。falseと0は省略として扱いません。SQL側で明示的に型変換すると、NULLでも型が確定します。
5. 配列ごとに「まとめるSQL列」を指定します。例えば `plans[]` は `plan_date,use_id`、`plans[].controls[]` は空欄（1行1要素）です。親グループごとに子配列を作るため、違う日付・typeの配下への混入も不一致になります。
6. レスポンス項目にSQL列名を入力します。空欄はDBとの値照合対象外です。`correct_point`はJSON列全体、または中身を個別に対応付けます。両方の重複設定は拒否します。
7. 期待する成功statusを指定し、追加 → 保存 → 準備 → レビュー → 実行します。SQL・パラメータ・配列の設定もレビュー対象です。

「計画取得の対応例を設定」は入力項目とレスポンスの対応例を埋めるだけです。SQL、実際に送るJSON、接続先は人が指定します。グループ列に日付だけを入れるとtypeを混ぜてしまう場合があるため、まとめる単位は仕様に従って選びます。同一グループのprofitなどが不一致なら、勝手に先頭値を採用せず、実行前に設定不整合として停止します。

## 判定と証跡

SQL結果から期待JSONを作り、指定した項目を比較します。配列は件数・値・重複・所属グループを含めて一対一に照合し、順序は配列ごとに無視／一致を選べます。順序一致の場合はSQLにORDER BYを明示してください。1行1要素では同値のSQL行も削除しません。JSON列全体はキー順を無視し、JSON内の配列順とboolean／数値の違いを保持します。

日時や時刻の返却形式はSQLの `AT TIME ZONE`・`to_char` などで明示します。ツールは日付の丸め・タイムゾーン・履歴優先順位を推測しません。DBのnumericはDecimalとして比較します。

`db_sql_response_comparison`に定義、渡したパラメータ、取得行・件数、期待JSON、実レスポンス、OK/NGを保存します。合否は既存のExcel・JUnit・HTML・UIに反映します。設定変更は試験IDに反映するため、変更前のレビューを流用しません。

## 計画取得のサンプルについて

`examples/plan-get/`にOpenAPI・送信JSON・期待値SQL・試験設定を用意しています。`scenario.json`は既存のシナリオファイル読み込みでも利用できます。

**これはツール機能を検証するための明示的な例で、提示されたPHPの完全な再現ではありません。** コードの欠けた箇所、期間変数を作る処理、応答を組み立てる処理は不明です。次の例示条件を実APIに合わせて変更してください。

- GET JSON body、`start <= datetime < end`、Asia/Tokyoで日付・時刻へ変換。
- site_id優先、location_idはt_siteから参照。
- correct省略なら両方を候補、type指定時はそれを選択。
- 日時/use_idごとに `(correct OR force)`、fixed/cpbs_typeの順位、createdで1行を選択。
- type省略時は固定・force候補があればcreated降順・use_id順の先頭、それ以外はh_settingの最新設定から選択。元コードのLIMIT 1やlast集約の完全な意味を推測したものではなく、検証用に選択を確定した例です。
- 日付＋typeでplansをまとめ、各行をcontrolsにする。dateはYYYY-MM-DD、timeはHH:MM、期間の応答はリクエスト値を返す例。
- enum、必須項目、JSONのnull可否、ゼロ件時の応答、認証は本番仕様に合わせてください。サンプルは接続認証なしの検証用APIです。

## 制限

- 比較前にSQLを実行します。APIとの同一スナップショットは保証できないため、比較対象データの同時更新を止めた検証環境で実行してください。
- PostgreSQLの読み取り専用トランザクション、30秒の文タイムアウト、5秒のロック待ち、最大5000行です。上限超過は未確認として停止し、切り捨てて合格にはしません。
- SQLはレビュー済みのものを使用し、可能ならSELECT権限のみの接続ユーザーを使ってください。読み取り専用トランザクションは任意関数の外部副作用まで隔離するSQLサンドボックスではありません。
- SQLが0行で、対応項目が配列内だけなら空配列と照合できます。ルートのsite_idなどもSQL列と対応付けている場合、値を導けないため未確認でAPI実行前に停止します。ゼロ件時のstatusやルート値は、別の明示したレスポンス確認ケースで設定してください。
- SQLと対応付けた範囲の比較です。APIと同じSQLのコピーだけでは、その検索ルール自体のバグは検出できません。仕様から作った既知データ・期待値での確認を併用してください。

## 検証

`runner/tests/test_sql_response_e2e.py`は実PostgreSQL・HTTP APIで、入力の指定／省略、h_settingへのフォールバック、優先順位、親子配列の照合を検証します。APIは期待値SQLを再利用せずPythonで選択し、正解が分かる値も直接assertします。故障を注入し、欠落・余分・重複・値違い・履歴・別拠点・別type・グループ違いをNGにすることを確認します。

`gui/tests/test_browser_sql_response.py`は実ブラウザから設定・保存・レビュー・実行し、成功／失敗のExcelを取得します。
