# API Test Automation Roadmap

**Goal:** OpenAPI がない素の PHP 案件を含め、API 仕様確認から試験書・実行・DB 判定・結果報告までをローカル GUI で段階的に自動化する。

**Spec:** `docs/superpowers/specs/2026-09-22-local-api-test-automation-design.md`

## 実施原則

- 各フェーズは単独で動作・検証・配布できる状態で完了させる。
- `src/` と `runner/` の既存エンジンは回帰テストで保護し、段階的に統合層から呼び出す。
- 新機能は同じフェーズ内で Tauri GUI から利用可能にする。
- GitHub Actions を完了条件にせず、ローカル検証コマンドを正とする。
- PHP 解析の推定値は根拠・信頼度・要確認状態を保持し、人の承認前に確定仕様として扱わない。
- 各フェーズの計画は直前フェーズの実装結果を反映して別文書として作成する。

### フェーズ 2: 素の PHP から Copilot を使った OpenAPI 草案

進め方: PHPソースをCopilotに読ませることが許可されたため、初稿はVS CodeのCopilot Chatで作る。ローカルGUIから依頼文をコピーし、生成された下書きと根拠・要確認事項を取り込んで人が確認する。独自のPHP静的解析器は実案件でCopilotの不足が分かってから範囲を決める。

成果:

- Copilot用のPHP調査プロンプト
- OpenAPI 3.x草案と根拠・要確認事項
- GUIでの下書きの検証と確認済み操作
- 代表的なPHP記法での精度評価

計画開始条件:

- 実案件または匿名化サンプルから、URL と PHP の対応方式、PHP バージョン、入力取得の代表記法を確認できる。

完了ゲート:

- OpenAPI がない代表 PHP サンプルから、既存 parser が読める草案と要確認一覧を生成できる。
- 人が承認した草案をフェーズ 1 の Layer 1 ワークフローへ渡せる。

### フェーズ 4: 精度向上

進捗（2026-09-23）: ローカルSchemathesisをTauri GUIへ追加。GET中心の探索、ローカルJUnit/HTML/VCR、token秘匿、Windowsプロセスツリーキャンセルを実装し、loopback APIで認証あり・なし・不正認証の拒否チェックも検証した。決定論的認証試験は OpenAPI の OR/AND 要件を読み取り、API キーの header/query/cookie 配置と通常ログイン認証からの分離に対応した。応答本文を追加送信なしで検査し、明確なPHP実行時エラー、Python/一般的なスタックトレース、SQLSTATEと一般的なDB構文エラー、PEM秘密鍵ブロック、OpenAPI `writeOnly` 項目、GitHub・Slack・AWSアクセスキーID・Stripeの既知形式が表へ露出した場合は、内部パスや機密値を再掲せずNGにする。結果Excelでも、スキーマ上の `writeOnly` 項目（配列・動的キー・oneOf/anyOf内を含む）、秘密鍵・既知トークン・一般的な秘密項目名・認証系ヘッダーの値を伏せる。既知形式の限定検査であり、任意のトークンやJWTを網羅するものではない。JUnitの失敗IDを抽出し、Tauri UIから失敗ケースだけを再実行する導線も実装済み。素のPHPからCopilotが出すSQL根拠JSONをTauriのDB対応表生成へ任意入力でき、operationIdとPostgreSQL実スキーマを照合する。根拠行をmapping.yamlへ残し、一致しても確信度は「中」、複数候補や不一致は自動選択しない。DB準備画面から選択済みファイルのパスを差し込んだCopilotシナリオレビュー依頼文をコピーできる。今回、DBシナリオで役割別ログインボディを選ぶ `auth_profile` と、セッション分離、他人所有データを作る `given` 間の参照を追加し、ケースレビューにも役割名を記録する。Copilot依頼文には安全な単発入力注入候補の出力条件を追加した。残りは実APIの権限・注入ケースを開発VMで確認し、API/DB固有の期待値をレビューする工程。


成果:

- DB スキーマと PHP SQL からの対応候補
- 前提データと DB チェック候補
- Copilot 用レビュー素材
- ローカル Schemathesis
- 基本セキュリティ試験
- 発見した失敗の固定回帰ケース化

計画開始条件:

- 開発 VM で安全に実行可能な操作、認証方式、対象 DB、Copilot へ渡せる情報の社内規則を確認できる。

完了ゲート:

## 順序の理由

PHP 解析を先に GUI へ直接追加すると、現在の `main.js` が持つ CLI 引数構築、設定、一時ファイル、進捗解析の責務がさらに増える。フェーズ 1 で統合境界を作ることで、以降の PHP 解析、試験ケースマスター、Schemathesis は同じワークフロー契約へ追加できる。

フェーズ 2 と 3 は密接だが、PHP 解析結果の形が実案件で安定する前に共通試験モデルを確定すると推定情報の表現を誤る可能性がある。そのため、まず OpenAPI 草案と要確認情報を実用化し、その結果を踏まえて正式な試験ケースマスターを定義する。
