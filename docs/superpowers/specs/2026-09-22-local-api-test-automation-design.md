# ローカル完結型 API 試験自動化ツール 要求・設計仕様

作成日: 2026-09-22  
対象リポジトリ: `api-tester`

## 1. 目的

開発用 VM 上で稼働する API と DB を対象に、API 仕様の把握、試験設計、前提データ準備、試験実行、判定、試験書・結果報告書作成までをローカル PC 上の GUI から可能な限り自動化する。

人が API 仕様と業務上の期待結果をレビューし、最終結果を承認することを前提とする。ツールは人の判断を置き換えず、調査・転記・ケース作成・実行・証跡作成の工数と漏れを減らす。

## 2. 利用条件と制約

- 対象 API は主にフレームワークを使用していない PHP で実装されている。
- OpenAPI 定義が存在しない案件を主要な利用ケースとする。
- OpenAPI 3.x 定義が存在する案件も同じワークフローで扱う。
- API サーバーと DB は開発用 VM 上で稼働する。
- ソースコードを GitHub へ保存しない。
- GitHub Actions、Pull Request、Issues、GitHub 上の成果物保存など、GitHub リポジトリを必要とする機能に依存しない。
- GitHub Copilot はローカルエディタ内の補助としてのみ利用できる。
- API 仕様、ソースコード、リクエスト、レスポンス、DB データを外部クラウドへ自動送信しない。
- 正式な GUI は Tauri 版とする。
- 通常操作は GUI 内で完結させる。CLI は内部エンジンおよび保守用インターフェースとして残す。
- Windows で実行可能な形式を提供する。初期段階では Python の別途導入を許容し、最終段階でランタイム同梱を目指す。

## 3. 成功条件

利用者が対象 PHP プロジェクトまたは OpenAPI 定義、API の Base URL、必要に応じて DB 接続先を指定すると、以下を実施できること。

1. API 仕様候補を生成する。
2. 自動判定できない箇所を「要確認」として明示する。
3. 人が確認できる試験ケースマスターと試験仕様書を生成する。
4. 承認された内容に従って前提データを準備し、API 試験を実行する。
5. HTTP レスポンスと DB 状態を自動判定する。
6. 実行内容と一致する証跡、結果報告書を生成する。
7. 失敗ケースを選択して再実行できる。

「完全自動」の意味は、業務上の正しさをツールが独断で決めることではない。人が確認した仕様と期待結果について、その後の準備・実行・判定・帳票作成を自動化することを指す。

## 4. 基本方針

全面的な再実装は行わない。既存の OpenAPI 解析、テスト生成、HTTP 実行、DB 検証、帳票出力を再利用し、その前段と統合部分を新設する。

### 4.1 流用する既存資産

- `src/`: OpenAPI 解析、`$ref` 解決、パラメータ抽出、境界値・異常値生成、Excel/JSON 出力
- `runner/`: HTTP 実行、認証、Cookie、multipart、並列実行、レスポンス検証
- `runner/db_*`: PostgreSQL・InfluxDB 接続、DB 前提データ、DB 検証、不変条件、後片付け
- `runner/junit_writer.py`: JUnit XML 出力
- `gui-tauri/`: 正式 GUI とネイティブシェル
- 既存の Python、JavaScript、Rust のテストと Lint

### 4.2 新設する領域

- PHP ソース解析
- API 仕様候補と信頼度の管理
- OpenAPI 草案生成・レビュー
- 共通試験ケースマスター
- ワークフロー統合サービス
- ローカル Schemathesis 実行
- 基本セキュリティ試験
- HTML 結果レポート
- 配布用 Python ランタイムまたはサイドカー

## 5. 対象ワークフロー

```text
PHPソース / OpenAPI / DBスキーマ / 既存資料
                    │
                    ▼
             対象プロジェクト登録
                    │
                    ▼
          API候補・DB対応関係の自動解析
                    │
                    ▼
       OpenAPI草案 + 要確認事項 + 信頼度
                    │
                    ▼
               人によるレビュー
                    │
                    ▼
             試験ケースマスター
              ├── 試験仕様書
              ├── 決定論的API試験
              ├── 探索的API試験
              ├── DB業務シナリオ
              └── 基本セキュリティ試験
                    │
                    ▼
          自動実行・自動判定・証跡保存
                    │
                    ▼
             結果報告書・人の承認
```

## 6. コンポーネント設計

### 6.1 GUI

GUI は内部ファイルや CLI オプションではなく、作業工程を表示する。

1. 対象を登録
2. API 仕様を確認
3. 試験内容を確認
4. 試験を実行
5. 結果を確認

通常表示する入力は次を基本とする。

- PHP プロジェクトまたは OpenAPI ファイル
- API Base URL
- 出力先

認証、DB 接続、タイムアウト、並列数、セキュリティ試験などは必要な場合だけ開く詳細設定へ配置する。

### 6.2 ワークフローサービス

Tauri GUI が各 Python スクリプトの引数を直接組み立てる構造を段階的に廃止し、統合されたワークフロー API を介して処理する。

ワークフローサービスは次を担当する。

- プロジェクト設定の保存・読込
- 各処理の開始・キャンセル
- 進捗イベントの統一
- 成果物パスの管理
- 一時ファイルと機密情報の管理
- エラーの利用者向け表現
- 既存 `src/`・`runner/` の呼び出し

### 6.3 PHP 解析

初期対応は素のPHPを対象にする。PHPソースをCopilotに読ませることが許可されたため、OpenAPI初稿とレビュー資料はCopilot Chatに作らせる。独自の静的解析器は、この方法で実案件の不足が確認できた場合に範囲を決める。Copilotには次を調べさせる。

- PHP ファイルと URL 候補
- HTTP メソッド
- `$_GET`、`$_POST`、`$_COOKIE`、`$_FILES`
- `php://input` から読み取る JSON
- ヘッダー参照
- 必須、型、文字数、数値範囲、列挙値に相当する検証
- `http_response_code()` などのステータスコード
- `json_encode()` されるレスポンス候補
- SQL が参照・更新するテーブルとカラム
- 認証・認可処理の候補

PHPは記述方法が統一されていないため、レビュー資料には出典と未確認事項を残す。将来、機械的な抽出器を追加する場合は、次の信頼度を使う。

- 高: 直接的な構文から確定できる
- 中: 共通関数や単純なデータフローから推定できる
- 低: 動的 include、動的 SQL、動的ルーティングなど推定要素が大きい
- 要確認: 根拠不足または候補が競合する

解析不能な項目を推測で確定値にしない。

### 6.4 動的確認

下書きと根拠資料を開発VM上の実APIと照合する。

- エンドポイントの存在
- HTTP メソッド
- ステータスコード
- Content-Type
- レスポンス構造
- 認証要求
- PHP エラー、スタックトレース、5xx

初回探索では安全な読み取り操作を優先する。POST、PUT、PATCH、DELETE は開発環境であることと前提・後片付け方法を確認した後に実行する。

### 6.5 OpenAPI 草案

初稿はCopilotがPHPソースからOpenAPI 3.x草案を生成する。動的確認とDBスキーマとの照合は、必要に応じて後続工程で追加する。

- 根拠が確定した項目は通常の OpenAPI として出力する。
- 不確実な項目はツール内部のレビュー情報として保持する。
- OpenAPI 標準を壊す独自情報は、確定版へ無条件に混入させない。
- GUI で要確認事項を一覧表示し、承認・修正・除外できるようにする。
- 確定した OpenAPI は既存 `src/` へ渡す。

### 6.6 試験ケースマスター

試験設計と実行結果の単一の情報源として、言語非依存の共通モデルを導入する。

最低限、次の情報を持つ。

- 試験 ID
- 出典と生成根拠
- 自動生成／人手追加／人手確認済みの状態
- 対象 API と HTTP リクエスト
- 前提データ
- 期待レスポンス
- 期待 DB 状態
- 不変条件
- 後片付け
- 実行結果
- リクエスト・レスポンス証跡
- 判定と判定理由

既存 Excel と `scenarios.yaml` は直ちに廃止せず、共通モデルへの入出力アダプターとして維持する。

### 6.7 試験実行

#### 決定論的試験

既存 Layer 1 を利用し、型、必須、enum、境界値、oneOf/anyOf、multipart、ヘッダー、Cookie、認証、レスポンススキーマ、応答時間を検証する。

#### 探索的試験

Schemathesis をローカルプロセスとして GUI から実行する。GitHub Actions を前提としない。

- 失敗リクエストをローカルへ保存する。
- 再現できる失敗を試験ケースマスターへ昇格できるようにする。
- 外部クラウドレポート機能を使用しない。

#### DB 業務シナリオ

既存 Layer 2 を利用し、DB への前提データ投入、API 実行、レスポンス確認、DB 確認、不変条件、後片付けを行う。作成 API が存在しないリソースは DB へ直接投入できるようにする。

### 6.8 Copilot 補助

Copilotはアプリの実行時依存にしない。素のPHPからOpenAPI初稿を作る際にはVS CodeのCopilot Chatを使い、ツールは依頼文を提供する。後続の試験設計にも次の素材を用いる。

- PHP 解析で判断できなかった OpenAPI 項目
- 業務ルール・状態遷移・権限制御の試験候補
- DB シナリオ候補
- レビュー観点

Copilot の回答は候補として取り込み、人が承認するまで実行対象にしない。Copilot が存在しなくても既存試験機能は動作する。

### 6.9 基本セキュリティ試験

通常試験に含める安全な範囲は次とする。

- 認証なし、不正な認証情報、権限不足。OpenAPI の `security` にある OR 候補と AND 要件を集約して未認証・無効値プローブを生成し、API キーは header/query/cookie の配置を反映する。認証プローブは通常のログイン認証や保持 Cookie を引き継がない。
- 必須欠落、型不正、想定外フィールド
- 過長文字列、過大配列
- Content-Type、HTTP メソッドの不一致
- SQL インジェクション・XSS・パストラバーサルを模した単発入力
- 5xx の期待値検証と、レスポンス本文に含まれる明確な PHP 実行時エラー・Python traceback・Stack trace・SQLSTATE/DB例外識別子・PEM秘密鍵ブロックの検出。OpenAPI の `writeOnly` 項目がレスポンスに現れた場合も検出する。GitHub・Slack・AWSアクセスキーID・Stripeの既知形式も検査する。検出詳細にはレスポンス本文、機密値、内部パスを再掲しない。結果Excelへレスポンスを記録する際も、OpenAPI `writeOnly` 項目、秘密鍵、既知形式の資格情報、一般的な秘密項目名の値、認証系ヘッダーを伏せる。既知形式の限定検査であり、任意のトークンやJWTを網羅するものではない。

大量リクエスト、総当たり、巨大ファイル、DoS 相当、広範な ID 列挙は通常試験へ含めない。将来追加する場合は危険試験として別画面・明示的承認・上限設定を必要とする。

### 6.10 帳票と証跡

同じ試験ケースマスターから以下を生成する。

- 事前レビュー用試験仕様書 Excel
- 実行後の試験結果報告書 Excel
- HTML 結果レポート
- JSON
- JUnit XML
- リクエスト・レスポンス証跡
- 再実行可能な失敗ケース

試験仕様書と実際の実行内容は同じ試験 ID で対応させる。実送信内容の証跡は `PreparedRequest` 等の実物から生成し、別系統で再構築しない。認証情報、Cookie、パスワードなどはマスキングする。

## 7. データと安全性

- DB 接続情報と認証情報を成果物へ平文で出力しない。
- 一時ファイルは成功、失敗、キャンセル、プロセス起動失敗の全経路で削除する。
- 前提データには試験実行 ID を付与し、本番・既存データと区別する。
- 作成した前提データの主キーを記録し、依存関係の逆順で削除する。
- クリーンアップ失敗を警告だけで隠さず、結果報告書へ残す。
- SQL の値はパラメータ化し、識別子は許可された形式のみ受け付ける。
- 更新系試験は開発環境向けであることを GUI に表示する。

## 8. エラー処理

- 内部例外をそのまま GUI の主要メッセージへ表示しない。
- GUI には利用者が次に取れる行動を日本語で表示する。
- 詳細ログには原因、対象ファイル、処理段階を記録する。
- PHP 解析の不確実性はエラーではなく「要確認」として扱う。
- 一部 API の解析失敗でプロジェクト全体の解析結果を失わない。
- キャンセル後に次工程を開始しない。

## 9. テスト戦略

- 既存テストを移行中の回帰基準として維持する。
- PHP 解析は実際の記述パターンを小さなフィクスチャとして蓄積する。
- OpenAPI 草案は構文検証と既存 parser への読込で検証する。
- ワークフローは各段階の成功、失敗、キャンセル、再開を検証する。
- GUI は設定の往復、無効化状態、主要導線、エラー表示を Vitest で検証する。
- API 実行はローカル HTTP サーバーを使う統合テストを維持する。
- DB 試験は単体テストに加え、利用可能な環境で PostgreSQL 統合テストを行う。
- GitHub Actions に依存せず、ローカルで全検証を実行できるコマンドを提供する。

## 10. 段階的な提供

### フェーズ 1: 既存機能の統合境界

- ワークフローサービスの最小インターフェース
- プロジェクト設定と成果物管理
- 既存 OpenAPI 試験と DB 試験を統合 API 経由で実行
- GUI の主要導線を工程中心に整理

この段階で既存機能が新 GUI 導線から利用できることを完成条件とする。

### フェーズ 2: Copilotを使った素のPHPからOpenAPI草案

- Copilot用のPHP調査プロンプト
- 出典と要確認事項を伴うOpenAPI草案
- GUIによる下書き検証と確認済み操作
- 実案件での抽出精度評価

代表的な素のPHPから、Copilotがレビュー可能なOpenAPI草案と根拠資料を作り、人が確認してから既存試験へ渡せることを完成条件とする。

### フェーズ 3: 共通試験ケースマスターと試験書

- 共通モデル
- 既存 Excel・YAML アダプター
- 事前試験仕様書
- 実行結果の同一 ID 反映
- HTML 結果レポート

試験書に記載されたリクエストと実行されたリクエストの対応を機械的に追跡できることを完成条件とする。

### フェーズ 4: 精度向上

- DB 対応関係と前提データ候補
- 業務シナリオ候補と Copilot 用素材
- ローカル Schemathesis
- 基本セキュリティ試験
- 失敗ケースの固定化と再実行

### フェーズ 5: 配布

- Python ランタイムまたはサイドカーの同梱
- インストーラー
- オフライン環境での起動・実行確認
- バージョン情報と診断情報

## 11. 対象外

- 業務仕様を人の確認なしで確定すること
- Copilot の回答を無審査で実行すること
- 本番環境への自動的な破壊的試験
- 一般的なソースコード脆弱性診断ツールの完全な代替
- 負荷・耐久・DoS 試験の無条件実行
- 初期段階から全 PHP 記法や全 DB 製品を網羅すること
- 既存 Python コアの Rust への全面移植

## 12. 初期対応範囲と拡張方針

- PHP: 素の PHP を優先し、実プロジェクトで確認できた記法をフィクスチャとして追加する。
- DB: 現在の PostgreSQL と InfluxDB を維持する。追加 DB は共通バックエンドインターフェースを定義した後、案件要求に応じて追加する。
- OpenAPI: JSON と YAML の両方を入力として扱い、内部では同じモデルへ正規化する。
- OS: Windows を初期の配布対象とする。

## 13. 未確定事項

実装開始前に全てを確定する必要はないが、該当フェーズまでに次を決める。

1. 対象 PHP のルーティング方式（URL と PHP ファイルの一対一、共通 `index.php`、独自ルーター等）
2. PHP の対応バージョン
3. DB の製品・バージョンと追加優先順位
4. 社内試験書 Excel テンプレートの列・書式・承認欄
5. 認証方式の代表例
6. 更新系 API を探索実行してよい環境の識別方法
7. ソースコードと DB スキーマの持ち出し・Copilot 参照に関する社内規則

未確定事項は、対象案件を登録するときにプロジェクト設定として明示する。根拠がない既定値で自動確定しない。

## 14. 受入基準

- GitHub へ接続せず主要機能を実行できる。
- OpenAPI がある案件では、現行機能と同等以上の試験を GUI から実行できる。
- OpenAPI がない代表的な素の PHP 案件では、API 候補、OpenAPI 草案、要確認事項を生成できる。
- 人が承認した試験ケースから試験仕様書を生成できる。
- 同じ試験ケースを自動実行し、HTTP と DB を判定できる。
- 試験仕様書、実行証跡、結果報告書を同じ試験 ID で追跡できる。
- エラー、キャンセル、プロセス起動失敗時にも機密情報と一時ファイルが残らない。
- 既存の自動テストが回帰せず、新規機能に対応するテストが追加されている。
