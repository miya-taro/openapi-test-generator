# 計画POST・計画GET・pwrcoの認証付き検証

2026-10-13更新。独立した検証用APIに認証層を組み合わせ、実HTTP・実PostgreSQL・DB試験ランナーで確認しました。利用者の実APIサーバーへの接続試験ではありません。

ログインは `POST /v1/auth/login`、レスポンスの `id` を `auth-key` ヘッダに設定します。認証拒否時の401は未確定仕様の仮置きです。

| API | 認証付きで再実行した既存ケース | 認証なし | 不正ID | 拒否時のDB変更なし |
| --- | ---: | --- | --- | --- |
| 計画POST | 28（正常25・部分保存を禁止する入力異常3） | 401 | 401 | 保存先・拠点参照テーブルを確認 |
| 計画GET | 32（条件組み合わせ27・期間境界5） | 401 | 401 | 計画・拠点・設定テーブルを確認 |
| pwrco/set | 38（正常18・入力異常20） | 401 | 401 | 保存先・拠点参照テーブルを確認 |

全98ケースが認証付きで期待結果と一致しました。追加で各APIの認証なし・不正IDの6ケースが合格しました。拒否時にはバックエンドの処理が呼ばれていないことと、DBスナップショットの一致も独立に確認しています。

`test_plan_coverage_e2e.py`では別途、計画POSTの自動生成異常220件をログイン済みの状態で実行し、400とDB変更なしを確認しています。Content-Type試験時に認証ヘッダが落ちる不具合を、この組み合わせで発見・修正しました。ケースファイルと詳細は `examples/plan-test-suites/README.md` に記載しています。

故障の検出:

- 認証を無視して処理する: 3つ全てでNGを検出。
- 401を返す前に保存してしまう: 計画POST・pwrcoでNGを検出。HTTPは期待どおり401でも、DB差分で不合格になる。

実CLIの `--auth-config` も3つ全てで確認しました。ランナー自身がログインし、取得したidを送ってDB照合し、Excel・JUnit・JSON証跡を出力します。ログインのパスワードを誤らせると終了コード3で停止し、後続APIを呼ばず、DBも変わりません。

再実行には専用PostgreSQLの接続設定を `OTG_INTEGRATION_DB_CONFIG` に設定します。

```sh
python -m pytest runner/tests/test_three_api_auth_e2e.py -q -s
```

証跡は `OTG_THREE_AUTH_EVIDENCE_DIR` に保存可能です。CIでは `measure-get-evidence/three-api-auth` 配下に保存します。正常時のExcel/JUnitとJSON、認証拒否・故障検出のJSONをAPIごとに分けています。今回の新規検証は実HTTP/DBとCLIの組合せであり、3つそれぞれのUI操作を追加で再検証したものではありません。UIの共通ログイン設定は別の `test_browser_login.py` で検証しています。

期限切れ・更新・権限別アクセス・ログアウト後の無効化は仕様未提示のため未確認です。
